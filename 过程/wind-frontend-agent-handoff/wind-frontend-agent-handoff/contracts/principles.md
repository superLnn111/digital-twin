# 工程与架构指导原则（Project Engineering Charter）

用途：沉淀项目负责人的核心工程品味与底线要求，供后续所有重构、新功能开发及 Agent（Codex 等）代码审查长期复用。

---

## 1. 核心设计哲学：KISS 与反 AI 屎山铁律

1. **朴素实现优先，实在不行再加（YAGNI）**：
   - 面对需求先写最直白、无状态或少状态的朴素实现，不要提前为假想的极端并发、极端损坏或未来扩展造框架。
   - 能通过删减组件、合并链路或调整参数（如增大分段周期）解决的问题，严禁通过叠加后台打包进程、虚拟文件系统或复杂缓存层来打补丁。
   - 砍掉“伪可配置性”与多版本协商：在单一硬件、单一场景的项目中，清晰的常量与单一格式远胜于复杂的抽象工厂与多版本兼容层。
2. **单一事实源（Single Source of Truth），消灭双写与对账**：
   - 严禁把同一份状态同时记录在目录树、`commit.json`、`receipt.json`、`manifest.jsonl` 和 SQLite 多处，再去写上千行的对账（reconcile）代码。
   - 文件系统本身（或单张索引表）就是唯一事实源：文件以 `.tmp` 写入，写完 `fsync` 原子改名即代表“已提交”，文件存在即有效，无需多层回执文件。
3. **用“无尽数据流”代替“会话生命周期状态机”**：
   - 传感器采集本质是像行车记录仪或 `journald` 一样的连续数据流，按时间切块落盘、按块上传、磁盘满时淘汰已上传旧块。
   - 避免设计复杂的会话状态机（如 `recording -> processing_pending -> finalizing -> completed`），消除因“会话收尾（finalization）”卡死而阻塞新采集的隐患。
4. **失败即退出（Crash-Only / Fail-Fast），把恢复交给操作系统**：
   - 不在业务代码中编写复杂的自愈状态机、后台守护看门狗或死锁重试逻辑。
   - 遇到硬件断开或不可恢复 I/O 错误时，打印清晰错误日志后直接以非零状态码退出，交由 `systemd` 的 `Restart=on-failure` 与 `RestartSec` 原生机制拉起。
   - 意外掉电或强杀留下的未封口 `.tmp` 尾部残片，原地保留但不再读取，不在服务启动时扫描、删除、搬移或抢救。60 秒段未封口时可能丢失接近一分钟数据，加上尚未落盘的队列内容，不能表述为只丢几百毫秒。
5. **拒绝防御性仪式与校验玄学**：
   - 不在受控内部目录做逐级 `lstat` 符号链接防御，不给不可变本地文件发明免检证书体系（如算源码哈希的 `layout_proof`）。
   - 校验只做单次必要边界检查（串口帧加和校验、网络传输外层哈希、压缩流自带校验），不在内部模块间反复重读重算。
6. **只写黑盒契约测试，拒绝白盒实现绑定测试**：
   - 测试只验证公开接口与端到端数据契约（例如：喂入一段原始串口字节流，验证落盘与上传后解码出的帧序列完全一致）。
   - 严禁为内部私有函数、临时目录结构编写大量脆弱的白盒单元测试，防止测试集反过来绑架架构、阻碍重构。

## 2. 技术栈与依赖克制：原生、标准库与声明式优先

1. **吃透语言标准库，拥抱最新稳定版（Python 3.15），极力克制第三方重型依赖**：
   - 新项目直接采用最新 `nixpkgs-unstable` 与 **Python 3.15.0**，优先使用标准库内置能力：`compression.zstd`（流式压缩）、`sqlite3`（本地状态与轻量索引）、`tomllib`（配置解析）、`struct`（二进制帧编解码）。
   - 除非吞吐或分析场景被实测证明标准库撑不住，否则不默认引入重型 C++/Rust 扩展依赖，保持依赖树极简。
2. **NixOS 原生与声明式管理**：
   - 配置通过 Nix 声明式落盘；服务生命周期、启停顺序、权限和目录初始化优先交由 `systemd`（`systemd.services`、`systemd.tmpfiles`）和文件系统原生机制处理。
   - 严禁编写运行时自检、自动补配置、自动修权限或轮询健康状态的自定义包装脚本。
3. **模块物理隔离与单向依赖**：
   - 共享协议层只放纯数据协议与编解码，零业务状态、零第三方依赖。
   - 采集端（`gateway`）、云端（`cloud`）、离线分析端（`analysis`）物理隔离，严禁跨服务相互 import 内部实现。

## 3. 文档组织：消灭流水账，只留活契约

1. **全仓只保留核心契约文档**：
   - `README.md`：项目一页纸总览、硬件拓扑、构建与运行命令。
   - `docs/principles.md`：本工程指导原则。
   - `docs/storage-and-architecture.md`：架构边界、磁盘存储格式与故障处理规则。
   - `docs/api-contract.md`：后端 HTTP/WebSocket 接口定义、请求参数与响应示例。
2. **禁止把历史日志当文档**：
   - 废除按日期追加的 `current-state.md`、阶段性验收小作文和冗余 ADR。
   - 代码与接口变更时直接原地更新对应契约文档，历史演进交由 Git Commit 记录追溯。

## 4. Agent 协作与操作边界（甲乙方规约）

1. **目标导向与方案对齐**：
   - 甲方（负责人）定义目标、性能/体积指标、依赖红线与禁区；乙方（Agent）若在调研中发现比参考基线更简洁、更契合上游生态的实现方向，应先提交简短方案对比说明依据与代价，经甲方批准后实施。
   - 讨论设计时每次给一个主推方案（最多一个备选），不罗列庞大的选项菜单。
2. **显式变更审批**：
   - 任何改变读写语义、权限边界、资源限额或日常使用习惯的决定，必须先挑明问题与代价，经甲方批准后再落代码，严禁暗中增加限额、特判、降级或兜底。
3. **只读取证与实机隔离**：
   - Agent 负责代码编写、本地构建求值与隔离模拟验证；涉及真实树莓派或生产云端服务器的 `switch`、服务重启、网络切换等状态变更，一律交由甲方手动执行或显式授权。
4. **数据安全红线**：
   - “减法”仅针对受 Git 管理的代码与配置；真实实验数据、未跟踪文件、密钥与数据库内容在任何清理或重构中均视为只读资产，严禁擅自删除、覆盖或移动。

## 当前采集与迁移合同

- 采集在内存完成帧同步与加和校验。段中仅保存完整、校验通过的厂商帧；坏帧和串口噪声只保留统计，不再承诺原始串口全字节可恢复。未知消息 ID 只要帧校验通过仍保留。
- 每通道约 60 秒切段，在完整帧边界切分。未完整帧留在解析器内存，归入收到剩余字节后的下一段，不写跨段上下文。
- 每个新帧采用补齐该帧的 read 返回时刻。UTC 纳秒和单调时钟纳秒均保留；它们不是设备采样时钟。历史迁移保留原接收时间及其原有语义。
- 一个段是独立的标准 Zstd 文件。只用固定宽度整数编码，不做自研预测、变长时钟编码、二次合包、跨版本分派和内部重复对账。
- 采集按通道使用 wind-capture@.service，读入缓冲每路 1 MiB。服务启停小于 1 秒是隔离验证目标，不是整机冷启动保证。
- 预览是 1 Hz、只保留最新值的非持久通道；完整有效帧以已封口段为准。自动磁盘淘汰默认关闭，未来只允许显式启用后处理新目录中已获云端确认的段。
- 历史迁移只核对有效帧序列、原有时间戳和质量统计。一次性旧格式读取工具、转换数据与核对报告放在仓库外。旧仓库、原始数据和云端 .uploading 隔离文件保持原样。

- 云端只接受带内容校验的单个Zstd段；压缩/解压内容上限分别为8/16 MiB。HTTP帧分页默认100、最多1,000条，每次最多扫描两个段并返回继续游标，不静默丢弃后续数据。
- 新API使用独立Bearer认证。反向代理只对新前缀关闭继承的Basic Auth，旧站点认证保持；凭据通过systemd LoadCredential传入，不进入仓库或Nix store。
